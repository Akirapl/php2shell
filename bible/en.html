0. TL;DR and one-page overview

In one paragraph. Around 13:34 UTC on 21 October 2026, the PHP security team published 8.5.12, 8.4.27, 8.3.36 and 8.2.35 and two GitHub advisories for critical engine bugs: CVE-2026-109618 (“RCE via OOM corruption”) and CVE-2026-109619 (“RCE via stale global state”), both CVSS v4.0 9.2 [P][1][2][3]. Both stem from the same pattern: when PHP aborts a request under emergency conditions (especially out-of-memory), it can leave internal state pointing at memory that no longer exists — and a later step or a later request on the same worker can use that “ghost”. On Apache + mod_php, unauthenticated remote code execution was demonstrated before any application code runs [P][3:1]. Wiz Research claims discovery with Calif and OpenAI, using frontier AI models heavily [D][4]. A Thursday 22 Oct embargo broke with a 20 Oct leak, forcing PHP to pre-announce and pull the release forward by a day [P][5][6]. In the Netherlands, Belgium, France and Finland, some sites went offline as a precaution [P][7]. As of this version’s cutoff there is no independently confirmed in-the-wild exploitation; reports conflict [?].

Key facts

What is new here [A]: (1) a bug in the runtime, not the app; (2) AI in discovery and — researchers say — in making exploitation practical; (3) an embargo leak that became a ~22-hour race; (4) precautionary public-site takedowns in several EU countries before a patch existed.

1. Background: PHP on the web and the request lifecycle

1.1 How large PHP is

Rasmus Lerdorf created PHP in 1994 (as “Personal Home Page Tools”) and released its source code to the public in June 1995 [P][9]. Per W3Techs (21 Oct 2026), PHP is used by 69.3% of websites whose server-side language is known; among PHP sites, 65.2% run version 8, 27.0% version 7, 7.7% version 5, 0.1% version 4 [P][10]. WordPress, Drupal, Joomla, Magento and MediaWiki all run on PHP [D][4:1].

Method note [A]: “69.3%” is of sites with a recognized server-side language, not “the whole Internet”. Headlines like “70% of the Internet” (Wiz) are simplifications [D][4:2].

1.2 What happens when a browser asks for a page

PHP is usually embedded in a web server or run as a pool of workers. The glue is called a SAPI (Server API).

  • Apache mod_php
    • How it works: PHP inside Apache processes (typically prefork: many processes, each handling requests in sequence).
    • Why it matters for PHP2Shell: Worst case: request shutdown always runs, even when startup failed [P][1:1].
  • PHP-FPM
    • How it works: Separate PHP pool; nginx/Apache via FastCGI.
    • Why it matters for PHP2Shell: On failed startup FPM kills the child — breaks the simplest path; others remain [P][1:2][2:1].
  • CGI / php-cgi
    • How it works: Classically one process per request (or FastCGI).
    • Why it matters for PHP2Shell: Listed as affected [P][3:2].
  • FrankenPHP
    • How it works: Modern PHP application server.
    • Why it matters for PHP2Shell: Source analysis: likely mod_php-like on shutdown [P][1:3].
  • LiteSpeed LSAPI
    • How it works: FPM-like model.
    • Why it matters for PHP2Shell: App-specific paths “likely, unvalidated” [P][1:4].

Analogy [A]: a PHP worker is a clerk’s desk. Each request is a case file. After the case, every folder must be put away. If the lights go out in a panic (OOM / fatal), a sticky note with a folder address may remain for a folder that was already shredded. The next visitor — same desk — treats that address as live. That is “stale global state” and “OOM corruption”.

1.3 Why this matters

Most critical PHP-ecosystem bugs live in applications. Here the bug is in the engine [P][3:3]. A “Hello World” app on an affected version is still exposed [D][4:3]. Inventory must cover CMSes, control panels, appliances with PHP in firmware, and hidden php.exe binaries [D][11][12].

2. The vulnerabilities, in depth

2.1 Shared pattern

Official advisories and the Wiz blog describe variants of the same cross-request memory-safety failure [P][1:5][2:2][4:4]:

  1. An operation stores request-owned state in a worker-global location (producer).
  2. A fatal / OOM / diagnostic aborts before the matching reset.
  3. Request memory is freed; the global still points at it.
  4. The same worker handles another request.
  5. An operation before normal initialization reads that pointer (consumer) → use-after-free → with a suitable heap layout: RCE.

Why memory-safety bugs in a runtime are hard [A]: they are not “one hole in function X” but an interaction of allocator, error handling (longjmp / bailout), many extensions and many SAPIs. The fix had to change OOM strategy and reset a wide set of globals (~400 files) [P][13].

2.2 CVE-2026-109618 — RCE via OOM corruption

What was wrong. PHP used longjmp() on OOM to leave the current context and abort the request. When request memory was only partly initialized, that early exit left invalid state; shutdown could treat it as valid [P][1:6].

OOM strategies (concepts only) [P][1:7]: multipart without a usable Content-Length; unbounded part headers (more memory than on the wire); empty file controls not counting toward max_file_uploads but still creating metadata. Application behavior can also reach OOM.

Why mod_php is worst. Apache mod_php unconditionally runs request shutdown even when startup failed. Body parsing during startup can exhaust memory_limit in the invalid-state window — before the application runs [P][1:8][3:4]. FPM exits the child on failed startup; source analysis still treats FPM as susceptible, but no complete FPM exploit for 618 was demonstrated [P][1:9].

The fix. Remove longjmp() for OOM → soft OOM at a VM safe point + hard OOM via _exit() at a second threshold [P][1:10][13:1].

2.3 CVE-2026-109619 — RCE via stale global state

What was wrong. Worker-global state (error / session / object / extension) can point at request memory. A fatal, OOM or diagnostic leaves a stale pointer; a later request consumes it before normal initialization [P][2:3].

Confirmed consumers [P][2:4]:

  • INI diagnostics before init — warnings/deprecations while applying settings (.htaccess / php_value on mod_php; PHP_VALUE on FPM) before the executor initializes. Hiding diagnostics does not help.
  • Session upload progress — can reach session handling before ordinary initialization; independent of the INI path.

Strongest demonstrated case: fatal_error_backtraces (PHP 8.5) + a diagnostic → confirmed RCE on mod_php. Session upload-progress RCE: confirmed on mod_php and FPM [P][2:5].

Wiz’s four classes (grouped under two CVEs) [D][4:5]: upload-progress unserializer UAF; PHPSESSID memory disclosure; fatal-backtrace UAF; OPcache type confusion. Directionally aligned with the GHSA; chain detail is from Wiz.

2.4 CVSS v4.0 decoded

Both CVEs: CVSS:4.0/AV:N/AC:H/AT:P/PR:N/UI:N/VC:H/VI:H/VA:H/SC:N/SI:N/SA:N → 9.2 [P][1:11][2:6].

Field Value Meaning
AV:N Network Remotely reachable
AC:H High High attack complexity (heap layout, conditions)
AT:P Present Preconditions in the system
PR:N None No authentication
UI:N None No user interaction
VC/VI/VA:H High Full impact on confidentiality, integrity, availability of the vulnerable system
SC/SI/SA:N None No scored impact on subsequent systems

Early chatter said “CVSS 10.0” [D][14][5:1] — PHP’s official score is 9.2 with AC:H and AT:P.

2.6 Incomplete mitigations

PHP and core developers stress: the only complete mitigation is updating [P][3:6][17]. Temporary measures (e.g. memory_limit=-1, session.upload_progress.enabled=0, on 8.5 fatal_error_backtraces=0) shrink specific paths; they do not make an install safe [P][3:7]. Do not use RLIMIT_AS/RLIMIT_DATA as substitutes — they can force the vulnerable mmap→longjmp path [P][1:13].

3.2 What AI changes in bug hunting

Wiz: the vulnerable code had been present for more than a decade; building a working chain meant combining multiple bugs and adapting to memory layouts — frontier models “substantially reduced that barrier” [D][4:14]. BSI expects large-scale exploitation “within a few hours” of the updates, because attackers can analyse them quickly with AI-assisted tools [P][19].

[A] That does not mean “AI found the CVE alone”. It means the cost of going from a hard memory-safety bug to credible RCE across many targets fell. The same economics apply to attackers (patch reverse-engineering) and defenders (triage).

The PHP Foundation (14 Oct 2026) described using Daybreak Red (OpenAI) to validate reports and sort the queue — context for a surge of AI-assisted submissions [P][20].

3.3 The 2024 audit and the Ecosystem Security Team

In 2024 Quarkslab (Sovereign Tech Agency / OSTIF) found 17 security-relevant findings; heise notes a similar class of issue had already sparked remediation debate [P/D][21][12:2]. In May 2026 the PHP Foundation announced an Ecosystem Security Team [D][12:3]. PHP2Shell shows both investment in security and a long architectural tail around bailout/OOM [A].

4. Coordinated disclosure 101 and how it went here

4.1 Coordinated disclosure 101

Typical flow [A]: (1) private report; (2) confirm and fix; (3) embargoed notice to distros/LTS and selected partners; (4) simultaneous advisories + releases; (5) ecosystem messaging. Goal: shrink the window between attacker knowledge and patch availability.

4.2 How it went here

  1. Report and remediation (Aug–Oct 2026) — per Wiz [D][4:15]. Commit “Avoid state corruption via bailout” on 18 Oct 2026; annotated tags on 19 Oct [P][13:2][22].
  2. Early access. php.net: “Linux distributions and LTS vendors received the patches in advance” [P][3:9]. Wiz lists Automattic, Akamai, AWS, Cloudflare, Fastly, Google, Imperva, Microsoft, Vercel and others for pre-day-zero mitigations [D][4:16]. watchTowr pushed Active Defense mitigations to watchTowr Platform clients before the patch [P][23].
  3. Embargo. watchTowr: originally Thursday 22 Oct, 11:00 ET (= 15:00 UTC) [P][5:2].
  4. Pre-announcement after the leak. At 19:33 UTC on 20 Oct, Jakub Zelenka (bukka) announced Wednesday 21 Oct 14:00 UTC, reserving the right to ship earlier if details leaked or exploitation appeared [P][24].
  5. Trade-off [A]: the notice gave ~18 h for inventory and patch windows, but also confirmed the CVEs were real and drew attacker attention. OpenSSL 3.0.7 (2022) showed another variant: a CRITICAL pre-announce later downgraded to HIGH after prenotification feedback [P][25]. Here the 9.2 score held.

Process criticism (Kevin Beaumont, 21 Oct, 08:07 UTC): cyber vendors “who have advanced notice told customers details”, which he called “effectively reselling open-source project intelligence for profit” and summed up as “Protecting the ivory tower sucks” [P][26]. That tension returns with every infrastructure embargo [A].

5. The leak and the name “PHP2Shell”

5.1 What leaked, when and where

Times in UTC.

  • 20 Oct 15:20 — “Tell HN: 2x PHP RCE CVEs with CVSS 10.0 Incoming” (petecooper) — CVE numbers, “22 October 2026 at 18:00 CEST”; later deleted [P][14:1]. Time check: the post went up at 15:20 UTC (17:20 CEST) on 20 Oct and named 22 Oct 18:00 CEST (= 16:00 UTC), while watchTowr gave the embargo as 22 Oct 11:00 ET (EDT, = 15:00 UTC = 17:00 CEST) — two pre-disclosure accounts one hour apart; we cannot tell which matched the real embargo [?][5:3]. The PHP Foundation later named a third value, 22 Oct 14:00 UTC [P][8:1]
  • 20 Oct 16:39 — Kevin Beaumont (Mastodon): leak of the CVE numbers [P][27]
  • 20 Oct 18:26 — watchTowr: “supposed to wait until Thursday 11am ET… We can confirm that they're real.” [P][5:4]
  • 20 Oct 19:33 — Official PHP announcement [P][24:1]
  • 20 Oct 20:27 — Kirill Firsov: “php2shell” video (~1.7M views); tool banner “PHP2SHELL — PHP >= 5.4.0 RCE by Calif.IO” (Dormann screenshots) [P][28][29]
  • 21 Oct 00:30 — J4ck3LSyN claims a “reproduction”; later retracts the main RCE path [P/D][30]

HN commenter “bwoebi” (identity unverified): the video was why the announcement happened “at that moment” [D][31]. The timestamps contradict this: the announcement went out at 19:33 UTC, the video at 20:27 UTC, and the PHP Foundation says the video followed the pre-announcement [P][24:2][28:1][8:2].

5.2 The name

“PHP2Shell” does not come from PHP’s official notice. It came from the tool banner in the leaked demo (Calif.IO) and spread through media; BSI notes the marketing comparison to Log4Shell [P/D][32][33]. PHP uses descriptive CVE/GHSA titles [P][3:10].

5.3 Effect of the leak

PHP moved the day from Thursday to Wednesday and reserved an earlier release [P][24:3][6:1]. Tarballs and GHSA ultimately shipped ~26 minutes before the announced 14:00 UTC (tarballs Last-Modified 13:33:59 UTC, first GHSA 13:34:13 UTC) [P][34][2:7]. The embargo bought distros time but did not prevent a public “zero-day feeling” for ~22 hours [A].

6. Patch day

6.1 Release mechanics

  • Annotated tags php-8.2.35…php-8.5.12 created on 19 Oct (Panteleev, Mann, Buckley, Scherzer) — preparation before day zero [P][22:1].
  • Tarball php-8.5.12.tar.xz: Last-Modified: Wed, 21 Oct 2026 13:33:59 GMT [P][34:1].
  • GHSA-6wmf-4rv5-p3rp: 13:34:13Z; GHSA-w8hw-w9fx-j79w: 13:34:25Z; publisher: bukka [P][1:15][2:8].
  • The php.net Atom feed stamps T00:00:00Z on release day — a date convention, not the publication hour [P][35].

6.2 Size of the fix

Commit 31c0ea7 “Avoid state corruption via bailout”: +11,556 / −1,017 in 423 files (GitHub’s commit API lists only the first 300; the 8.2-branch commit touches 389); UnwindExit instead of OOM bailout + global resets [P][13:3]. Not “a few lines” — hence distro lag and regression risk in rushed backports [A].

6.3 “Patch released” ≠ “patched”

State ~14:00 UTC 21 Oct:

  • php.net source / Windows binaries — available [P][3:11]
  • Docker official library/php — PR #1694 opened 13:44; after merge still official-images + builds [P][36]
  • Remi (rpms.remirepo.net) — no update “today” — PHP Foundation warning [P][37]
  • Ubuntu tracker — CVE entries, “Needs evaluation” on many releases [P][38]
  • Debian/RHEL packages — in progress / not verified in this research [?]
  • Shared hosting — depends on the host (heise: Uberspace planned a temporary PHP shutdown) [D][12:4]

Until workers run binaries that include the fix, the system is vulnerable — press release notwithstanding [A].

7. The exploit race

7.1 How attackers reverse-engineer patches (conceptually)

Without recipes [A]: given a large public diff (here: hundreds of files around OOM and global resets), analysts diff before/after, locate changed error paths, and reconstruct entry conditions. BSI explicitly ties pace to AI tooling [P][19:1]. CERT.at: exploit code online + easier patch reversing → exploitation “soon” after publication [P][39]. Sansec expected mass attacks within 15 minutes of release (as quoted by SecurityWeek) [D][40].

7.2 Fake and retracted PoCs — signal versus noise

  • Firsov video / Dormann screenshots (Calif.IO / lcfr) — not independently verified in this research [P/D].
  • jackalsyn.com: the author retracted the “cached-pointer” path as DEAD; rated the real bug CVSS 5.3 / “NOT RCE” — does not match the official 9.2 [D][30:1]. Treat as noise / partial LLM reconstruction.
  • GitHub: many “php2shell”/CVE repos (e.g. ikow/php2shell-poc) — Tenable warns unverified exploit code may be malware-laced [D][41].

7.3 Exploitation telemetry (conflicting)

  • Cloudflare Knecht 07:43 UTC — “early attacks emerging”; WAF stopgap [P][42]
  • Huntress (as of 21 Oct, 10:00 ET) — none in partner environments [P][11:1]
  • watchTowr FAQ — no ITW (as of their FAQ) [P][43]
  • NCSC-NL / BSI v1.0 — no confirmed abuse / keine bestätigten Ausnutzungen [P][16:1][32:1]
  • PHP team → ANP — no indication of active abuse [D][44]
  • Patchstack (NBC), Firsov — “reports of active exploitation” / “in the wild” [D][45][46] without IoCs; a Hadrian “at scale” claim relayed by Mattias Geniar no longer appears in his updated post [?]
  • CISA KEV — no entry (research ~13:46 UTC) [P][47]

Takeaway [A]: settling “is it ITW?” needs IoCs from large sensors or a KEV listing — messaging still conflicts.

7.4 After disclosure: attempts, no confirmed breaches (as of 22 Oct 2026, 10:30 UTC)

Added in version 1.1. Defensive summary, no exploit details. Ledger: CLM-0090…CLM-0102.

Before the patch

  • AWS (Amazon Threat Intelligence) says its MadPot honeypots recorded a PHP2Shell exploitation attempt on 17 Oct, four days before disclosure and during the embargo, from a commercial anonymisation network; how the actor got the information is unknown [D][48]. The 17 Oct attempt has one source; heise notes it may have targeted a different file-upload flaw [?][49].
  • AWS also saw several PoCs and attempts between about 02:00 and 08:00 UTC on 21 Oct, before the 14:00 UTC release, from varied infrastructure that suggests multiple actors [D][48:1].
  • Cloudflare CEO Matthew Prince separately reported “thousands of attempts” in the 10 hours before the announcement, rising to “millions” by early 22 Oct [D][50]. Attempts before the patch therefore have two independent sources (AWS, Cloudflare). Both cover the period after the 20 Oct leak; only the 17 Oct attempt falls inside the embargo, and it is single-source [A].

Attempts versus breaches

  • After the release AWS calls PHP2Shell “broadly exploited in the wild”, but says it is unclear whether any attempt would have succeeded on real systems [D][48:2].
  • VulnCheck (via PCMag): at least one attempt against CVE-2026-109618 failed with a 404; two other addresses probed frequently [D, single source][51].
  • watchTowr (Jake Knott, via SecurityWeek): the exploits being sprayed “either don’t work at all, test for timing-based differences, or crash the target” [D][52].
  • CrowdStrike (Amit Serper, 21 Oct) says it verified the full chain in the lab: a single anonymous POST request made an Apache mod_php worker launch a shell and run a command, with no authentication and no vulnerable application code [D][53]. According to CrowdStrike, PHP’s shipped defaults (post_max_size 8M, memory_limit 128M) cannot be driven into the bug along the path it demonstrated; exposed are configurations where memory_limit is below roughly 4 × post_max_size, for example limits raised for large uploads [D][53:1]. The only server-side trace is said to be a memory-exhaustion fatal error ending in “in Unknown on line 0” in the web server log [D][53:2]. This does not contradict watchTowr: the exploits circulating publicly fail, and CrowdStrike has not published its own [A].
  • Recorded Future (Insikt Group), as of 21 Oct 19:00 UTC: the reporting does not establish the extent of successful exploitation or confirmed compromises [D][54].
  • heise (22 Oct, 07:23 UTC): no reports of successful attacks at the time of writing [D][49:1]. CISA KEV still has no entry (catalog 2026.10.21, checked 22 Oct 10:27 UTC) [P][47:1].

Precautionary takedowns

  • Germany (heise, citing dpa): Charité fully offline, parts of berlin.de switched off, the Berlin police online station unreachable, FU Berlin IT restricted; authority and police sites in Bavaria and Lower Saxony as well [D][49:2].
  • Reuters (via heise): government sites offline in Denmark, Finland, France and the Netherlands [D][49:3]. Denmark: Copenhagen Municipality, the Road Directorate, DMI and the school platform Aula; the minister called it a “global incident”, “not a cyberattack” [D][55].

Exposure (estimates, not counts of vulnerable systems)

  • Censys (via SecurityWeek): of 2.58 million internet-facing hosts seen on 21 Oct, about 1.58 million showed a PHP version and about 1.57 million were unpatched [D, estimate][52:1].
  • Unit 42 (via Nextgov): more than 22.6 million internet-exposed instances potentially vulnerable [D, estimate][56].
  • The numbers differ by method (hosts versus instances, version banners versus fingerprints), and a version banner can hide a distro backport [A].

End-of-life branches and backports

  • PHP fixed only 8.2–8.5 and published minimal source backports for 7.4, 8.0 and 8.1 [P][57]. Vendors went further on 21 Oct: Ubuntu USN-8948-1 (php8.1 on 22.04 LTS) [P][58], Freexian ELTS (php7.0, 7.3, 7.4) [P][59], deb.sury.org (packages back to 5.6) [P][60]. Branches without such a vendor stay exposed [A].

Takeaway [A]: as of 22 Oct the picture is “many attempts, no confirmed compromise”. For defenders: patch or take offline, and hunt back to at least 17 Oct, as AWS advises [D][48:3]. CrowdStrike’s result shows, however, that remote code execution is practically achievable on mod_php with some limit configurations [D][53:3].

8.1 Agencies

  • CERT-EU 2026-018 — Patch ASAP or isolate; “all from PHP 5”; CVSS → unauth RCE [P][15:1]
  • BSI — BITS-H Orange/3 + Caspers press: “großflächige Ausnutzung innerhalb weniger Stunden”; AI speeds reversing [P][32:2][19:2]
  • CERT-Bund — WID-SEC-2026-4055 (content behind login — unread here) [P/?]
  • NCSC UK — Identify PHP; patch; harden; consider offline; inventory bundled PHP [P][61]
  • NCSC-NL — Advisory; ncsc.nl offline; NCSC-NL/php2shell product list; no active abuse seen [P][16:2]
  • CERT.at — Update #1: exploit code online, functionality unconfirmed [P][39:1]
  • CERT Polska 195/2026 — Inventory; consider taking internet-facing PHP offline [P][62]
  • CERT-FR ALE-014 — upload_progress/multipart workarounds not qualified [P][63]
  • ACSC (ASD, Australia) / IPA (Japan) — pre-release alerts on 21 Oct: identify PHP and prepare to patch; ACSC was not aware of exploitation at publication [P][64][65]
  • CISA — No KEV for PHP2Shell at research time [P][47:2]

8.2 WAFs, hosts, CMSes

  • Cloudflare: Emergency Managed Ruleset — seven “Anomalous Execution” rules; Free plans included; Knecht: stopgap only [P][66][42:1].
  • CloudLinux Imunify360: WAF ruleset 8.83 blocks the circulating request pattern on ModSecurity/Coraza (log-only on LiteSpeed); the vendor calls it a virtual patch, not a fix [P][67]. bunny.net: managed Bunny Shield WAF rules, blocking only in WAF blocking mode; a stopgap — patch PHP [P][68].
  • Sansec (Magento): mass attacks in 15 minutes (via SecurityWeek); fix at infrastructure level, not in the store [D][40:1][33:1].
  • Wordfence / shared WP: the fix is not a WordPress auto-update — it depends on the host [D][69].

8.3 The Dutch (and neighbouring) shutdown wave

NOS/NU and the NCSC-NL notice document precautionary offline for DigiD.nl (site; DigiD login elsewhere partly still worked), MijnOverheid, Tweede Kamer, RIVM, ANWB, RTL, hospitals, SURF, parties, UWV (selected apps), NCSC.nl, NotuBiz, KNVB, charities, and more [P][7:1][44:1][70][16:3]. Belgium: Flemish government sites (Diependaele); France: prefectures; Finland: government sites [P][7:2].

Communications analysis [A]: a classic availability-versus-confidentiality/integrity trade-off. With CVSS 9.2, no reliable workaround, and a public PoC narrative, agencies chose “better a dark site than a owned server”. Cost: lost public services on a weekday. Log4Shell also saw radical isolation, but rarely such coordinated national IDP/portal takedowns in the hours before a patch.

9. Exposure and impact

9.1 What we know

  • W3Techs 21 Oct 2026: 69.3% / version split as above [P][10:1].
  • Modat 20 Oct: 4,384,302 services / 1,886,612 hosts; 79% of versioned services on EOL (4/5/7/8.0/8.1); largest group 7.4 (878,761); US/China/Japan/Germany lead hosts [D][71].
  • Mallory/THN: ~884k hosts with PHP ≤8.1 banners — banners, not confirmed vulnerability [D][72].
  • Tenable/Cutler/Poley: 1.3–1.9M host estimates [D][41:1].

9.2 What we do not know

  • How many hosts are both vulnerable and reachable via a working RCE path (SAPI, config, WAF).
  • How many were compromised before or just after the patch.
  • When LTS packages reach Remi / Docker Hub / shared hosting.
  • Whether CISA will add KEV and which IoCs vendors will publish.

10. Historical comparison

  • Log4Shell (CVE-2021-44228), Dec 2021 [P][73][74]
    • Similarities: Mass exposure of an “invisible” dependency; WAF stopgap; meme name
    • Pace / differences: Cloudflare: probes 8 days before disclosure; exploits 9 minutes after; Check Point: >800k attacks / 72 h
  • Heartbleed, Apr 2014 [P][75]
    • Similarities: Critical bug in Internet foundations; early notify of selected parties
    • Pace / differences: Google/Cloudflare knew before public; CRA Canada: ~900 SINs
  • PHP-CGI CVE-2024-4577, Jun 2024 [P][76][77]
    • Similarities: RCE in PHP; rapid weaponization
    • Pace / differences: Akamai: exploitation within 24 h; Imperva: TellYouThePass <48 h
  • OpenSSL 3.0.7 pre-announce, Oct–Nov 2022 [P][25:1]
    • Similarities: Public CRITICAL notice before details
    • Pace / differences: After prenotification downgraded to HIGH

24–72 h pattern [A]: after a public patch expect (1) mass scanning, (2) PoCs within hours, (3) ransomware/bots within 1–2 days if RCE is credible. With AI, BSI and Sansec assume hours, not days [P/D][19:3][33:2].

11. Lessons learned

For application developers

Do not assume “safe application code” protects against a runtime bug. Stay on supported PHP; avoid depending on rarely used pre-init features (upload progress) without need [A][3:12].

For ops / SRE

Inventory PHP including bundled copies (appliances, panels, containers). A patch window is not a press release — verify php -v / the package on every host. Plan B: isolate internet-facing systems when a patch is unavailable [P][61:1][15:2].

For open-source maintainers

Large memory-safety fixes need time and distro prenotification; embargo leaks are a real scenario — keep an “release earlier” plan (PHP had one and used it) [P][24:4].

For governments / CERTs

Precautionary shutdowns brake risk but cost trust in public services. Dependency inventories (NCSC-NL/php2shell) in the Log4Shell style are valuable [P][16:4].

For the media

Separate official CVSS 9.2 from “CVSS 10” rumors; CDN “early attacks” from CERT “no abuse”; community names from vendor notices. Do not treat unverified PoCs as “the exploit” [A].

Appendix C: Defensive checklist

How to verify you are patched — not how to attack.

  1. Find PHP: php -v on hosts; Docker images; panels; appliances; Windows php.exe / php-cgi.exe [D][11:2].
  2. Target versions: ≥ 8.5.12 / 8.4.27 / 8.3.36 / 8.2.35; for EOL — vendor LTS or upgrade [P][3:13].
  3. After update: restart all workers (FPM reload/restart, Apache graceful/restart); check the version in the real SAPI, not only CLI.
  4. Containers: once Hub tags exist — pull + redeploy; PR #1694 is only the start of the chain [P][36:1].
  5. Remi: do not wait for Remi’s “today” update — distro packages or build from source [P][37:1].
  6. Temporarily (not instead of patching): advisory measures; vendor WAFs as a stopgap [P][3:14][66:1].
  7. Post-facto hunting: unusual PHP child processes (shell, curl, wget); webshells; new docroot files; worker churn; odd multipart + 500s [D][11:3][4:19].
  8. Internet-facing EOL: upgrade, VPN, or offline [P][61:2][15:3].
