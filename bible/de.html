0. TL;DR und Ein-Seiten-Überblick

In einem Absatz. Am 21. Oktober 2026 gegen 13:34 UTC veröffentlichte das PHP-Sicherheitsteam die Versionen 8.5.12, 8.4.27, 8.3.36 und 8.2.35 sowie zwei GitHub-Advisories zu kritischen Engine-Schwachstellen: CVE-2026-109618 („RCE via OOM corruption“) und CVE-2026-109619 („RCE via stale global state“), beide CVSS v4.0 9.2 [P][1][2][3]. Beide folgen demselben Muster: Wenn PHP eine Anfrage im Notfall abbricht (besonders bei Speichermangel), kann interner Zustand auf Speicher zeigen, der nicht mehr existiert — und ein späterer Schritt oder eine spätere Anfrage desselben Workers kann diesen „Geist“ nutzen. Unter Apache + mod_php wurde unauthentifizierte Remote Code Execution bevor Anwendungscode läuft nachgewiesen [P][3:1]. Wiz Research beansprucht die Entdeckung gemeinsam mit Calif und OpenAI unter starker Nutzung von Frontier-KI [D][4]. In den Niederlanden, Belgien, Frankreich und Finnland gingen Sites vorsorglich offline [P][7]. Zum Redaktionsschluss dieser Fassung gibt es keine unabhängig bestätigte Ausnutzung „in the wild“; die Berichte widersprechen sich [?].

1. Hintergrund: PHP im Netz und der Request-Lebenszyklus

1.1 Wie groß PHP ist

Rasmus Lerdorf schuf PHP 1994 (als „Personal Home Page Tools“) und veröffentlichte den Quellcode im Juni 1995 [P][9]. Laut W3Techs (21.10.2026) nutzen 69,3 % der Websites mit bekannter Server-Sprache PHP; darunter 65,2 % Version 8, 27,0 % Version 7, 7,7 % Version 5, 0,1 % Version 4 [P][10]. WordPress, Drupal, Joomla, Magento und MediaWiki laufen auf PHP [D][4:1].

Methodischer Hinweis [A]: „69,3 %“ bezieht sich auf Sites mit erkannter Server-Sprache, nicht auf „das ganze Internet“. Schlagzeilen wie „70 % of the Internet“ (Wiz) sind Vereinfachungen [D][4:2].

1.2 Was passiert, wenn der Browser eine Seite anfordert

PHP steckt üblicherweise im Webserver oder läuft als Worker-Pool. Die Schnittstelle heißt SAPI (Server API).

  • Apache mod_php
    • Funktionsweise: PHP in Apache-Prozessen (typisch Prefork).
    • Bedeutung für PHP2Shell: Schlimmster Fall: Request-Shutdown läuft immer, auch wenn der Start scheiterte [P][1:1].
  • PHP-FPM
    • Funktionsweise: Eigener Pool; nginx/Apache per FastCGI.
    • Bedeutung für PHP2Shell: Bei Startfehler beendet FPM den Child — unterbricht den einfachsten Pfad; andere bleiben [P][1:2][2:1].
  • CGI / php-cgi
    • Funktionsweise: Klassisch ein Prozess pro Request (oder FastCGI).
    • Bedeutung für PHP2Shell: Als betroffen genannt [P][3:2].
  • FrankenPHP
    • Funktionsweise: Moderner PHP-Application-Server.
    • Bedeutung für PHP2Shell: Codeanalyse: wahrscheinlich wie mod_php beim Shutdown [P][1:3].
  • LiteSpeed LSAPI
    • Funktionsweise: FPM-ähnliches Modell.
    • Bedeutung für PHP2Shell: App-spezifische Pfade „wahrscheinlich, nicht validiert“ [P][1:4].

Analogie [A]: Ein PHP-Worker ist der Schreibtisch eines Sachbearbeiters. Jede Anfrage ist ein Vorgang. Danach müssen alle Akten weg. Geht das Licht in Panik aus (OOM / Fatal), bleibt vielleicht ein Zettel mit einer Adresse einer Akte, die schon geschreddert wurde. Der nächste Besucher — derselbe Schreibtisch — behandelt die Adresse als gültig. Das ist „stale global state“ und „OOM corruption“.

1.3 Warum das zählt

Die meisten kritischen Lücken im PHP-Ökosystem sitzen in Anwendungen. Hier sitzt der Bug in der Engine [P][3:3]. Eine „Hello World“-App auf betroffener Version ist ebenfalls exponiert [D][4:3]. Inventar muss CMSe, Control Panels, Appliances mit PHP im Firmware und versteckte php.exe umfassen [D][11][12].

2. Die Schwachstellen — tief erklärt

2.1 Gemeinsames Muster

Offizielle Advisories und der Wiz-Blog beschreiben Varianten desselben speicherbezogenen Fehlers an der Request-Grenze [P][1:5][2:2][4:4]:

  1. Eine Operation speichert request-eigenen Zustand in einer Worker-Globalen (Producer).
  2. Fatal / OOM / Diagnose bricht ab, bevor der passende Reset läuft.
  3. Request-Speicher wird freigegeben; die Globale zeigt weiter darauf.
  4. Derselbe Worker bedient eine weitere Anfrage.
  5. Eine Operation vor der normalen Initialisierung liest den Zeiger (Consumer) → Use-after-free → bei passendem Heap-Layout: RCE.

Warum Memory-Safety-Bugs in einer Runtime schwer sind [A]: Sie sind keine „eine Lücke in Funktion X“, sondern eine Wechselwirkung aus Allocator, Fehlerbehandlung (longjmp / Bailout), vielen Extensions und vielen SAPIs. Der Fix musste die OOM-Strategie ändern und ein breites Set von Globalen zurücksetzen (~400 Dateien) [P][13].

2.2 CVE-2026-109618 — RCE via OOM corruption

Was falsch war. PHP nutzte longjmp() bei OOM, um den Kontext zu verlassen und die Anfrage abzubrechen. War der Request-Speicher nur teilweise initialisiert, hinterließ der Early-Exit ungültigen Zustand; der Shutdown konnte ihn als gültig behandeln [P][1:6].

OOM-Strategien (nur Konzepte) [P][1:7]: Multipart ohne nutzbare Content-Length; unbegrenzte Part-Header (mehr Speicher als auf dem Draht); leere File-Controls zählen nicht zu max_file_uploads, erzeugen aber Metadaten. Auch Anwendungslogik kann OOM auslösen.

Warum mod_php am schlimmsten ist. Apache mod_php ruft den Request-Shutdown bedingungslos auf, auch wenn der Start scheiterte. Body-Parsing beim Start kann memory_limit im Fenster ungültigen Zustands erschöpfen — bevor die Anwendung läuft [P][1:8][3:4]. FPM beendet den Child bei Startfehler; die Quellanalyse hält FPM dennoch für anfällig, ein vollständiger FPM-Exploit für 618 wurde nicht gezeigt [P][1:9].

Der Fix. Entfernen von longjmp() für OOM → Soft-OOM am VM-Safe-Point + Hard-OOM mit _exit() bei einer zweiten Schwelle [P][1:10][13:1].

2.3 CVE-2026-109619 — RCE via stale global state

Was falsch war. Worker-globaler Zustand (Error / Session / Object / Extension) kann auf Request-Speicher zeigen. Fatal, OOM oder Diagnose hinterlässt einen stale Pointer; eine spätere Anfrage konsumiert ihn vor der normalen Initialisierung [P][2:3].

Bestätigte Consumer [P][2:4]:

  • INI-Diagnosen vor Init — Warnungen/Deprecations beim Anwenden von Settings (.htaccess / php_value bei mod_php; PHP_VALUE bei FPM), bevor der Executor startet. Diagnosen zu verstecken hilft nicht.
  • Session Upload Progress — kann Session-Handling vor gewöhnlicher Initialisierung erreichen; unabhängig vom INI-Pfad.

Stärkster nachgewiesener Fall: fatal_error_backtraces (PHP 8.5) + Diagnose → bestätigtes RCE auf mod_php. Session-Upload-Progress-RCE: bestätigt auf mod_php und FPM [P][2:5].

Wiz zu vier Klassen (unter zwei CVEs gruppiert) [D][4:5]: Upload-Progress-Unserializer-UAF; Memory Disclosure über PHPSESSID; Fatal-Backtrace-UAF; OPcache-Type-Confusion. Richtungsgemäß im Einklang mit den GHSA; Kettendetails stammen von Wiz.

2.6 Unvollständige Mitigations

PHP und Core-Entwickler betonen: der einzige vollständige Schutz ist das Update [P][3:6][17]. Temporäre Maßnahmen (z. B. memory_limit=-1, session.upload_progress.enabled=0, unter 8.5 fatal_error_backtraces=0) verkleinern konkrete Pfade; sie machen eine Installation nicht sicher [P][3:7]. RLIMIT_AS/RLIMIT_DATA nicht als Ersatz nutzen — sie können den verwundbaren mmap→longjmp-Pfad erzwingen [P][1:13].

3.2 Was KI am Bug Hunting ändert

Wiz: Der verwundbare Code war über ein Jahrzehnt präsent; eine funktionierende Kette erforderte das Verketten mehrerer Bugs und Anpassungen an Speicherlayouts — Frontier-Modelle „substantially reduced that barrier“ [D][4:14]. Das BSI hält eine „großflächige Ausnutzung innerhalb weniger Stunden“ nach Erscheinen der Updates für wahrscheinlich, weil Angreifer sie mit KI-gestützten Werkzeugen schnell analysieren können [P][19].

[A] Das heißt nicht „KI fand die CVE allein“. Es heißt, die Kosten vom schweren Memory-Safety-Bug zum glaubwürdigen RCE auf vielen Targets sanken. Dieselbe Ökonomie gilt für Angreifer (Patch-Reverse) und Verteidiger (Triage).

Die PHP Foundation (14.10.2026) beschrieb den Einsatz von Daybreak Red (OpenAI) zur Validierung von Reports und Sortierung der Queue — Kontext einer Welle KI-gestützter Meldungen [P][20].

3.3 Audit 2024 und Ecosystem Security Team

2024 fand Quarkslab (Sovereign Tech Agency / OSTIF) 17 sicherheitsrelevante Findings; heise erwähnt, dass eine ähnliche Klasse schon Remediationsdebatten ausgelöst hatte [P/D][21][12:2]. Im Mai 2026 kündigte die PHP Foundation ein Ecosystem Security Team an [D][12:3]. PHP2Shell zeigt sowohl Security-Investitionen als auch eine lange architektonische Spur um Bailout/OOM [A].

4. Koordinierte Offenlegung: Grundlagen und Ablauf

4.1 Coordinated Disclosure 101

Typischer Ablauf [A]: (1) private Meldung; (2) Bestätigung und Fix; (3) embargierte Benachrichtigung von Distros/LTS und ausgewählten Partnern; (4) gleichzeitige Advisories + Releases; (5) Ökosystem-Kommunikation. Ziel: Fenster zwischen Angreiferwissen und Patch-Verfügbarkeit minimieren.

4.2 Wie es hier lief

  1. Meldung und Remediierung (VIII–X 2026) — laut Wiz [D][4:15]. Commit „Avoid state corruption via bailout“ am 18.10.2026; annotated Tags am 19.10. [P][13:2][22].
  2. Early Access. php.net: „Linux distributions and LTS vendors received the patches in advance“ [P][3:9]. Wiz nennt Automattic, Akamai, AWS, Cloudflare, Fastly, Google, Imperva, Microsoft, Vercel u. a. für Mitigations vor Day Zero [D][4:16]. watchTowr rollte Active-Defense-Mitigations für Kunden der watchTowr-Plattform vor dem Patch aus [P][23].
  3. Embargo. watchTowr: ursprünglich Donnerstag, 22.10., 11:00 ET (= 15:00 UTC) [P][5:2].
  4. Vorankündigung nach dem Leak. Am 20.10. um 19:33 UTC kündigte Jakub Zelenka (bukka) Mittwoch, 21.10., 14:00 UTC an, mit dem Recht auf frühere Freigabe bei Leak oder Ausnutzung [P][24].
  5. Trade-off [A]: Die Ankündigung gab ~18 h für Inventar und Patch-Fenster, bestätigte aber auch die Realität der CVEs. OpenSSL 3.0.7 (2022) zeigte eine andere Variante: CRITICAL-Preannounce, später auf HIGH abgestuft [P][25]. Hier hielt die 9.2.

Prozesskritik (Kevin Beaumont, 21.10., 08:07 UTC): Cyber-Anbieter mit Vorabinformation hätten Kunden „Details mitgeteilt“ – für ihn „faktisch ein gewinnorientierter Weiterverkauf von Wissen aus Open-Source-Projekten“ („Protecting the ivory tower sucks“) [P][26]. Diese Spannung kehrt bei jedem Infrastruktur-Embargo wieder [A].

5.2 Der Name

„PHP2Shell“ stammt nicht aus der offiziellen PHP-Mitteilung. Er kam vom Tool-Banner im geleakten Demo (Calif.IO) und verbreitete sich medial; das BSI notiert den Marketing-Vergleich zu Log4Shell [P/D][32][33]. PHP nutzt beschreibende CVE-/GHSA-Titel [P][3:10].

5.3 Wirkung des Leaks

PHP verschob den Tag von Donnerstag auf Mittwoch und behielt sich frühere Freigabe vor [P][24:3][6:1]. Tarbälle und GHSA erschienen schließlich ~26 Minuten vor den angekündigten 14:00 UTC (Last-Modified der Tarbälle 13:33:59 UTC, erstes GHSA 13:34:13 UTC) [P][34][2:7]. Das Embargo gab Distros Zeit, verhinderte aber kein öffentliches „Zero-Day-Gefühl“ für ~22 Stunden [A].

Solange Worker nicht auf Binaries mit dem Fix laufen, ist das System verwundbar — ungeachtet der Pressemitteilung [A].

7. Das Exploit-Rennen

7.1 Wie Angreifer Patches reverse-engineeren (konzeptuell)

Ohne Rezepte [A]: Bei großem öffentlichem Diff (hier: Hunderte Dateien um OOM und Global-Resets) vergleichen Analysten Vorher/Nachher, lokalisieren geänderte Fehlerpfade und rekonstruieren Eingangsbedingungen. Das BSI knüpft das Tempo ausdrücklich an KI-Werkzeuge [P][19:1]. CERT.at: Exploit-Code im Netz + erleichtertes Patch-Reversing → Ausnutzung „zeitnah“ nach Veröffentlichung [P][39]. Sansec erwartete Mass Attacks binnen 15 Minuten nach Release (zitiert von SecurityWeek) [D][40].

7.2 Falsche und zurückgezogene PoCs — Signal versus Rauschen

  • Firsov-Video / Dormann-Screenshots (Calif.IO / lcfr) — in dieser Research nicht unabhängig verifiziert [P/D].
  • jackalsyn.com: Autor widerruft den „Cached-Pointer“-Pfad als DEAD; bewertet den realen Bug mit CVSS 5.3 / „NOT RCE“ — stimmt nicht mit offiziellen 9.2 überein [D][30:1]. Als Rauschen / partielle LLM-Rekonstruktion behandeln.
  • GitHub: zahlreiche „php2shell“-/CVE-Repos (z. B. ikow/php2shell-poc) — Tenable warnt vor unverifiziertem Exploit-Code (Malware-Risiko) [D][41].

9.1 Was wir wissen

  • Modat 20.10.: 4.384.302 Dienste / 1.886.612 Hosts; 79 % der versionierten Dienste auf EOL (4/5/7/8.0/8.1); größte Gruppe 7.4 (878.761); USA/China/Japan/Deutschland führen bei Hosts [D][58].

  • Tenable/Cutler/Poley: Schätzungen 1,3–1,9 Mio. Hosts [D][41:1].

9.2 Was wir nicht wissen

  • Wie viele Hosts tatsächlich verwundbar und über einen funktionierenden RCE-Pfad erreichbar sind.
  • Wie viele vor oder kurz nach dem Patch kompromittiert wurden.
  • Wann LTS-Pakete Remi / Docker Hub / Shared Hosting erreichen.
  • Ob CISA KEV einträgt und welche IoCs Vendoren publizieren.

10. Historischer Vergleich

  • Log4Shell (CVE-2021-44228), XII 2021 [P][60][61]
    • Ähnlichkeiten: Massive Exposition einer „unsichtbaren“ Abhängigkeit; WAF-Stopgap; Mem-Name
    • Tempo / Unterschiede: Cloudflare: Probes 8 Tage vor Disclosure; Exploits 9 Minuten danach; Check Point: >800k Angriffe / 72 h
  • Heartbleed, IV 2014 [P][62]
    • Ähnlichkeiten: Kritischer Bug in Internet-Fundamenten; Early Notify Ausgewählter
    • Tempo / Unterschiede: Google/Cloudflare wussten vor Public; CRA Kanada: ~900 SIN
  • PHP-CGI CVE-2024-4577, VI 2024 [P][63][64]
    • Ähnlichkeiten: RCE in PHP; schnelle Bewaffnung
    • Tempo / Unterschiede: Akamai: Ausnutzung binnen 24 h; Imperva: TellYouThePass <48 h
  • OpenSSL 3.0.7 Pre-Announce, X–XI 2022 [P][25:1]
    • Ähnlichkeiten: Öffentliche CRITICAL-Ankündigung vor Details
    • Tempo / Unterschiede: Nach Prenotification auf HIGH abgestuft

Muster 24–72 h [A]: Nach öffentlichem Patch erwarten (1) Massenscans, (2) PoCs binnen Stunden, (3) Ransomware/Bots in 1–2 Tagen, wenn RCE glaubwürdig ist. Mit KI gehen BSI und Sansec von Stunden aus, nicht Tagen [P/D][19:3][33:2].

11. Lehren

Für Anwendungsentwickler

Nicht annehmen, „sicherer Anwendungscode“ schütze vor einem Runtime-Bug. Auf unterstütztem PHP bleiben; selten genutzte Pre-Init-Features (Upload Progress) nicht ohne Bedarf voraussetzen [A][3:12].

Für Ops / SRE

PHP inventarisieren einschließlich gebündelter Kopien (Appliances, Panels, Container). Patch-Fenster ≠ Pressemitteilung — php -v / Paket auf jedem Host prüfen. Plan B: Internet-facing Systeme isolieren, wenn kein Patch da ist [P][48:1][15:2].

Für Open-Source-Maintainer

Große Memory-Safety-Fixes brauchen Zeit und Distro-Prenotification; Embargo-Leaks sind real — „release earlier“-Plan bereithalten (PHP hatte einen und nutzte ihn) [P][24:4].

Für Regierungen / CERTs

Vorsorgliche Abschaltungen bremsen Risiko, kosten aber Vertrauen in öffentliche Dienste. Abhängigkeitslisten (NCSC-NL/php2shell) im Stil von Log4Shell sind wertvoll [P][16:4].

Für Medien

Offizielles CVSS 9.2 von „CVSS 10“-Gerüchten trennen; CDN-„early attacks“ von CERT-„kein Missbrauch“; Community-Namen von Vendor-Mitteilungen. Unverifizierte PoCs nicht als „den Exploit“ verkaufen [A].

Anhang C: Defensive Checkliste

Wie prüfen, dass Sie gepatcht sind — nicht, wie man angreift.

  1. PHP finden: php -v auf Hosts; Docker-Images; Panels; Appliances; Windows php.exe / php-cgi.exe [D][11:2].
  2. Zielversionen: ≥ 8.5.12 / 8.4.27 / 8.3.36 / 8.2.35; bei EOL — Vendor-LTS oder Upgrade [P][3:13].
  3. Nach dem Update: alle Worker neu starten (FPM Reload/Restart, Apache Graceful/Restart); Version im echten SAPI prüfen, nicht nur CLI.
  4. Container: sobald Hub-Tags existieren — pull + Redeploy; PR #1694 ist erst der Anfang der Kette [P][36:1].
  5. Remi: nicht auf Remis „heute“-Update warten — Distro-Pakete oder Build aus Source [P][37:1].
  6. Vorübergehend (nicht statt Patch): Maßnahmen aus den Advisories; Vendor-WAFs als Stopgap [P][3:14][53:1].
  7. Hunting danach: ungewöhnliche PHP-Child-Prozesse (Shell, curl, wget); Webshells; neue Docroot-Dateien; Worker-Churn; seltsames Multipart + 500 [D][11:3][4:19].
  8. Internet-facing EOL: Upgrade, VPN oder Offline [P][48:2][15:3].
