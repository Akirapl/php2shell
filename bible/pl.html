1. Tło: PHP w sieci i cykl życia żądania

1.1 Jak duży jest PHP

PHP stworzył Rasmus Lerdorf w 1994 r. (jako „Personal Home Page Tools”); kod źródłowy udostępnił publicznie w czerwcu 1995 r. [P][9]. Według W3Techs (21.10.2026) PHP używa 69,3% stron o znanym języku serwerowym; wśród nich 65,2% to wersja 8, 27,0% wersja 7, 7,7% wersja 5, 0,1% wersja 4 [P][10]. Na PHP działają m.in. WordPress, Drupal, Joomla, Magento i MediaWiki [D][4:1].

Zgodnie z metodologią [A]: „69,3%” to odsetek stron o rozpoznanym języku, nie „całego Internetu”. Nagłówki w stylu „70% of the Internet” (Wiz) to uproszczenia [D][4:2].

1.2 Cykl życia żądania (dla nie-ekspertów)

PHP zwykle nie „stoi samotnie”: jest wbudowany w serwer WWW albo działa jako pula procesów. Interfejs nazywa się SAPI (Server API).

  • Apache mod_php
    • Jak działa: PHP w procesach Apache (prefork: wiele procesów, każdy obsługuje żądania kolejno).
    • Znaczenie dla PHP2Shell: Najgorszy przypadek: shutdown jest wywoływany zawsze, nawet gdy start się nie powiódł [P][1:1].
  • PHP-FPM
    • Jak działa: Osobna pula; nginx/Apache przez FastCGI.
    • Znaczenie dla PHP2Shell: Przy nieudanym starcie FPM kończy childa — przerywa najprostszą ścieżkę; inne pozostają [P][1:2][2:1].
  • CGI / php-cgi
    • Jak działa: Klasycznie proces na żądanie (lub FastCGI).
    • Znaczenie dla PHP2Shell: Wymieniony jako podatny [P][3:2].
  • FrankenPHP
    • Jak działa: Nowoczesny serwer aplikacji.
    • Znaczenie dla PHP2Shell: Analiza kodu: prawdopodobnie jak mod_php przy shutdown [P][1:3].
  • LiteSpeed LSAPI
    • Jak działa: Model zbliżony do FPM.
    • Znaczenie dla PHP2Shell: Aplikacyjnie zależne ścieżki „prawdopodobne, nie zwalidowane” [P][1:4].

Analogia [A]: worker PHP to biurko urzędnika. Każde żądanie to sprawa na biurku. Po sprawie urzędnik powinien schować wszystkie teczki. Jeśli gasi światło w panice (OOM / fatal), może zostawić kartkę z adresem teczki, której już nie ma. Następny petent — to samo biurko — widzi adres i traktuje go jak ważny. Stąd „stale global state” i „OOM corruption”.

1.3 Dlaczego to ma znaczenie

Większość krytycznych luk w ekosystemie PHP dotyczy aplikacji (WordPress, wtyczki). Tu podatność jest w silniku [P][3:3]. Aplikacja „Hello World” na podatnej wersji też jest narażona [D][4:3]. Stąd skala: inventory obejmuje CMS-y, panele (cPanel/Plesk), appliances z PHP w firmware i ukryte php.exe [D][11][12].

2. Podatności — wyjaśnione w głąb

2.1 Wspólny wzorzec

Oficjalne biuletyny i blog Wiz opisują wariant tego samego problemu pamięciowego na granicy żądań [P][1:5][2:2][4:4]:

  1. Operacja zapisuje stan należący do żądania w lokalizacji globalnej workera (producent).
  2. Fatal / OOM / diagnostyka przerywa ścieżkę przed resetem.
  3. Pamięć żądania jest zwalniana; global nadal wskazuje na nią.
  4. To samo worker obsługuje kolejne żądanie.
  5. Operacja przed normalną inicjalizacją czyta ten wskaźnik (konsument) → use-after-free → przy odpowiednim układzie sterty: RCE.

Dlaczego błędy memory-safety w runtime są trudne [A]: nie są „jedną dziurą w funkcji X”, lecz własnością interakcji alokatora, obsługi błędów (longjmp / bailout), wielu rozszerzeń i wielu SAPI. Poprawka musiała zmienić strategię OOM i zresetować szeroki zestaw globali (~400 plików) [P][13].

2.2 CVE-2026-109618 — RCE via OOM corruption

Co było nie tak. PHP używał longjmp() przy OOM, by wyjść z kontekstu i przerwać żądanie. Gdy pamięć żądania była tylko częściowo zainicjalizowana, early-exit zostawiał invalid state; shutdown mógł go potraktować jak poprawny [P][1:6].

Strategie OOM (koncepcyjnie, bez przepisów) [P][1:7]: multipart bez użytecznego Content-Length; nieograniczona liczba nagłówków części (więcej pamięci niż na przewodzie); puste kontrolki plików nie liczą się do max_file_uploads, ale tworzą metadane. OOM może też wynikać z zachowania aplikacji.

Dlaczego mod_php jest najgorszy. Apache mod_php bezwarunkowo woła request shutdown, nawet gdy startup się nie udał. Body parsing przy starcie może wyczerpać memory_limit w oknie invalid state — zanim uruchomi się aplikacja [P][1:8][3:4]. FPM kończy childa przy nieudanym starcie; źródłowa analiza uznaje FPM za podatny, ale pełnego exploitu FPM dla 618 nie wykazano [P][1:9].

Poprawka. Usunięcie longjmp() dla OOM → soft OOM na VM safe point + hard OOM z _exit() przy drugim progu [P][1:10][13:1].

2.3 CVE-2026-109619 — RCE via stale global state

Co było nie tak. Globalny stan workera (error / session / object / extension) może wskazywać na pamięć żądania. Fatal, OOM lub diagnostyka zostawia stale pointer; kolejne żądanie konsumuje go przed normalną inicjalizacją [P][2:3].

Potwierdzeni konsumenci [P][2:4]:

  • Diagnostyki INI przed init — ostrzeżenia/deprecacje przy stosowaniu ustawień (.htaccess / php_value w mod_php; PHP_VALUE w FPM) zanim executor się zainicjalizuje. Ukrycie diagnostyk (error_reporting, @) nie chroni.
  • Session upload progress — może sięgnąć sesji przed zwykłą inicjalizacją; niezależny od ścieżki INI.

Najsilniejszy wykazany przypadek: fatal_error_backtraces (PHP 8.5) + diagnostyka → potwierdzone RCE na mod_php. Session upload progress RCE: potwierdzone na mod_php i FPM [P][2:5].

Wiz o czterech klasach (zgrupowanych pod dwoma CVE) [D][4:5]: upload-progress unserializer UAF; ujawnienie pamięci przez PHPSESSID; fatal backtrace UAF; OPcache type confusion. Kierunkowo zgodne z GHSA; szczegóły łańcuchów pochodzą od Wiz.

2.4 CVSS v4.0 — wektor pole po polu

Oba CVE: CVSS:4.0/AV:N/AC:H/AT:P/PR:N/UI:N/VC:H/VI:H/VA:H/SC:N/SI:N/SA:N → 9.2 [P][1:11][2:6].

2.6 Mitigacje niepełne

PHP i core developerzy podkreślają: jedyna pełna ochrona to update [P][3:6][17]. Środki tymczasowe (np. memory_limit=-1, session.upload_progress.enabled=0, na 8.5 fatal_error_backtraces=0) zmniejszają konkretne ścieżki, nie czynią instalacji bezpieczną [P][3:7]. Nie używać RLIMIT_AS/RLIMIT_DATA jako substytutu — mogą wymusić podatną ścieżkę mmap→longjmp [P][1:13].

3.2 Co AI zmienia w bug huntingu

Wiz: podatny kod był obecny ponad dekadę; zbudowanie działającego łańcucha wymagało łączenia wielu błędów i adaptacji do układów pamięci — frontier models „substantially reduced that barrier” [D][4:14]. BSI spodziewa się masowej eksploatacji „w ciągu kilku godzin” od wydania poprawek, bo atakujący mogą je szybko przeanalizować narzędziami AI [P][19].

[A] To nie znaczy, że „AI znalazło CVE sama”. Znaczy, że koszt przejścia od „trudnego błędu memory-safety” do wiarygodnego RCE na wielu targetach spadł. Ta sama ekonomia działa po stronie ataku (reverse patchy) i obrony (triage).

PHP Foundation (14.10.2026) opisała użycie Daybreak Red (OpenAI) do walidacji raportów i sortowania kolejki — kontekst rosnącej liczby zgłoszeń pisanych z pomocą AI [P][20].

3.3 Audyt 2024 i Ecosystem Security Team

W 2024 Quarkslab (zlecenie Sovereign Tech Agency / OSTIF) znalazło 17 findings z implikacjami bezpieczeństwa; heise zauważa, że podobny problem był przedmiotem sporów o remediację [P/D][21][12:2]. W maju 2026 PHP Foundation ogłosiła Ecosystem Security Team [D][12:3]. Incydent PHP2Shell pokazuje zarówno inwestycję w security, jak i długi ogon długu architektonicznego wokół bailout/OOM [A].

4. Skoordynowane ujawnienie: podstawy i przebieg

4.1 Coordinated disclosure 101

Typowy przebieg [A]: (1) prywatne zgłoszenie; (2) potwierdzenie i poprawka; (3) embargowane powiadomienie dystrybucji/LTS i wybranych partnerów; (4) jednoczesna publikacja advisories + wydań; (5) komunikacja ekosystemu. Cel: zminimalizować okno między wiedzą atakujących a dostępnością patchy.

4.2 Jak poszło tutaj

  1. Zgłoszenie i remediacja (VIII–X 2026) — wg Wiz [D][4:15]. Commit „Avoid state corruption via bailout” 18.10.2026; annotated tagi 19.10 [P][13:2][22].
  2. Early access. php.net: „Linux distributions and LTS vendors received the patches in advance” [P][3:9]. Wiz wymienia Automattic, Akamai, AWS, Cloudflare, Fastly, Google, Imperva, Microsoft, Vercel i innych przy mitigacjach przed dniem zero [D][4:16]. watchTowr wdrożył mitigacje Active Defense dla klientów platformy watchTowr przed patchem [P][23].
  3. Embargo. watchTowr: pierwotnie czwartek 22.10, 11:00 ET (= 15:00 UTC) [P][5:2].
  4. Pre-announcement po wycieku. 20.10 19:33 UTC Jakub Zelenka (bukka) ogłasza wydanie środa 21.10 14:00 UTC, z prawem do wcześniejszego wydania przy wycieku szczegółów lub eksploatacji [P][24].
  5. Trade-off [A]: zapowiedź dała ~18 h na inventory i okna patchowe, ale też potwierdziła realność CVE i przyciągnęła uwagę atakujących. OpenSSL 3.0.7 (2022) pokazał inny wariant: preannounce CRITICAL, potem obniżenie do HIGH po feedbacku prenotyfikowanych [P][25]. Tu ocena 9.2 utrzymała się.

Krytyka procesu (Kevin Beaumont, 21.10, 08:07 UTC): firmy cyberbezpieczeństwa, które dostały wcześniejsze powiadomienie, „przekazały klientom szczegóły” — według niego to „w praktyce odsprzedawanie dla zysku wiedzy projektów open source” („Protecting the ivory tower sucks”) [P][26]. To napięcie wraca przy każdym embargu infrastrukturalnym [A].

5.2 Nazwa

„PHP2Shell” nie pochodzi z oficjalnego komunikatu PHP. Wzięła się z banera narzędzia w wyciekłym demo (Calif.IO) i rozeszła się w mediach; BSI odnotowuje porównanie marketingowe do Log4Shell [P/D][32][33]. PHP używa tytułów opisowych CVE/GHSA [P][3:10].

5.3 Skutek wycieku

PHP przesunął dzień z czwartku na środę i zastrzegł wcześniejsze wydanie [P][24:3][6:1]. Finalnie tarballe i GHSA wyszły ~26 min przed zapowiedzianym 14:00 UTC (Last-Modified tarballi 13:33:59 UTC, pierwszy GHSA 13:34:13 UTC) [P][34][2:7]. Embargo dało dystrybucjom czas, ale nie ochroniło przed publicznym „poczuciem zero-day” przez ~22 h [A].

6. Dzień poprawki

6.1 Mechanika wydania

  • Annotated tagi php-8.2.35…php-8.5.12 utworzone 19.10 (Panteleev, Mann, Buckley, Scherzer) — przygotowanie przed dniem zero [P][22:1].
  • Tarball php-8.5.12.tar.xz: Last-Modified: Wed, 21 Oct 2026 13:33:59 GMT [P][34:1].
  • GHSA-6wmf-4rv5-p3rp: 13:34:13Z; GHSA-w8hw-w9fx-j79w: 13:34:25Z; publisher: bukka [P][1:15][2:8].
  • Feed Atom php.net stempluje T00:00:00Z w dniu wydania — to konwencja daty dnia, nie godzina publikacji [P][35].

6.2 Rozmiar poprawki

Commit 31c0ea7 „Avoid state corruption via bailout”: +11 556 / −1 017 w 423 plikach (API commitów GitHuba pokazuje tylko pierwsze 300; commit na gałęzi 8.2 zmienia 389); UnwindExit zamiast bailout OOM + reset globali [P][13:3]. To nie „kilka linijek” — stąd opóźnienie dystrybucji i ryzyko regresji przy pośpiesznym backportowaniu [A].

6.3 „Patch released” ≠ „patched”

Stan ~14:00 UTC 21.10:

  • php.net source / Windows binaries — dostępne [P][3:11]
  • Docker official library/php — PR #1694 otwarty 13:44; po merge jeszcze oficjalne-images + buildy [P][36]
  • Remi (rpms.remirepo.net) — brak update „dziś” — ostrzeżenie PHP Foundation [P][37]
  • Ubuntu tracker — wpisy CVE, status „Needs evaluation” na wielu release [P][38]
  • Debian/RHEL paczki — w toku / nie zweryfikowane w tym researchu [?]
  • Shared hosting — zależy od hosta (heise: Uberspace planował czasowe wyłączenie PHP) [D][12:4]

Dopóki worker nie działa na binariach z poprawką, system jest podatny — niezależnie od komunikatu prasowego [A].

7. Wyścig o exploit

7.1 Jak atakujący „czytają” poprawki (koncepcyjnie)

Bez podawania przepisów [A]: przy dużym, publicznym diffie (tu: setki plików wokół OOM i resetu globali) analitycy porównują „przed/po”, lokalizują zmienione ścieżki błędów i rekonstruują warunki wejścia. BSI wprost wiąże tempo z narzędziami AI [P][19:1]. CERT.at: pojawienie się kodu w sieci + ułatwienie reverse patcha → eksploatacja „zeitnah” po publikacji [P][39]. Sansec spodziewał się mass attacks w 15 min po release (cytowany przez SecurityWeek) [D][40].

7.2 Fałszywe i odwołane PoC — sygnał vs szum

  • Wideo Firsova / zrzuty Dormann (Calif.IO / lcfr) — niezweryfikowane niezależnie w tym researchu [P/D].
  • jackalsyn.com: autor odwołał ścieżkę „cached-pointer” jako DEAD; ocenił realny bug na CVSS 5.3 / „NOT RCE” — nie pokrywa się z oficjalnym 9.2 [D][30:1]. Traktować jako szum / częściową rekonstrukcję.
  • GitHub: liczne repo „php2shell”/CVE (m.in. ikow/php2shell-poc) — Tenable ostrzega przed niezweryfikowanym kodem (ryzyko malware) [D][41].

  • Huntress (stan na 21.10, 10:00 ET) — brak w partner environments [P][11:1]

8.2 WAF, hosty, CMS

  • Cloudflare: Emergency Managed Ruleset — 7 reguł „Anomalous Execution”; dostępne także Free; Knecht: stopgap only [P][53][42:1].
  • CloudLinux Imunify360: zestaw reguł WAF 8.83 blokuje krążący wzorzec żądań na ModSecurity/Coraza (na LiteSpeed tylko logowanie); producent nazywa to wirtualną łatką, nie poprawką [P][54]. bunny.net: zarządzane reguły WAF Bunny Shield, blokujące tylko w trybie blokowania; rozwiązanie doraźne — trzeba załatać PHP [P][55].
  • Sansec (Magento): mass attacks w 15 min (wg SecurityWeek); aktualizacja na poziomie infrastruktury, nie sklepu [D][40:1][33:1].
  • Wordfence / shared WP: fix nie idzie auto-updatem WordPressa — zależy od hosta [D][56].

8.3 Holenderska (i sąsiednia) fala wyłączeń

NOS/NU i komunikat NCSC-NL dokumentują profilaktyczne offline m.in.: DigiD.nl (strona; logowanie DigiD w innych systemach częściowo działało), MijnOverheid, Tweede Kamer, RIVM, ANWB, RTL, szpitale, SURF, partie, UWV (wybrane aplikacje), NCSC.nl, NotuBiz, KNVB, dobre cele (KWF, Amnesty…) [P][7:1][44:1][57][16:3]. Belgia: flamandzkie strony rządowe (Diependaele); Francja: prefektury; Finlandia: strony rządowe [P][7:2].

Analiza komunikacji [A]: to klasyczny trade-off availability vs confidentiality/integrity. Przy CVSS 9.2, braku pewnego workaroundu i publicznej PoC-narracji agencje wybrały „lepiej ciemna strona niż przejęty serwer”. Koszt: utrata usług publicznych w dzień roboczy. Precedent Log4Shell też widział radykalne izolacje, ale rzadko tak skoordynowane wyłączenia krajowych IDP/portali w godzinach przed patchem.

9. Ekspozycja i skutki

9.1 Co wiemy

  • W3Techs 21.10.2026: 69,3% / wersje 8·7·5 jak wyżej [P][10:1].
  • Modat 20.10: 4 384 302 usług / 1 886 612 hostów; 79% usług ze znaną wersją na EOL (4/5/7/8.0/8.1); największa grupa 7.4 (878 761); USA/Chiny/Japonia/Niemcy na czele hostów [D][58].
  • Mallory/THN: ~884 tys. hostów z banerem PHP ≤8.1 — banery, nie potwierdzona podatność [D][59].
  • Tenable/Cutler/Poley: szacunki 1,3–1,9 mln hostów [D][41:1].

9.2 Czego nie wiemy

  • Ile hostów faktycznie podatnych i osiągalnych ścieżką RCE (SAPI, konfiguracja, WAF).
  • Ile zostało skompromitowanych przed lub tuż po patchu.
  • Kiedy paczki LTS dotrą do Remi / Docker Hub / shared hosting.
  • Czy CISA wpisze KEV i jakie IoC opublikują vendorzy.

10. Porównanie historyczne

  • Log4Shell (CVE-2021-44228), XII 2021 [P][60][61]
    • Podobieństwa: Masowa ekspozycja „niewidzialnej” zależności; WAF stopgap; nazwa-mem
    • Tempo / różnice: Cloudflare: testy 8 dni przed disclosure; exploity 9 min po; Check Point: >800k ataków / 72 h
  • Heartbleed, IV 2014 [P][62]
    • Podobieństwa: Krytyczny bug w fundamencie; early notify wybranych
    • Tempo / różnice: Google/Cloudflare wiedzieli przed public; CRA CA: ~900 SIN
  • PHP-CGI CVE-2024-4577, VI 2024 [P][63][64]
    • Podobieństwa: RCE w PHP; szybka broń
    • Tempo / różnice: Akamai: eksploatacja w 24 h; Imperva: TellYouThePass <48 h
  • OpenSSL 3.0.7 pre-announce, X–XI 2022 [P][25:1]
    • Podobieństwa: Publiczna zapowiedź CRITICAL przed detalami
    • Tempo / różnice: Po prenotyfikacji obniżono do HIGH

Wzorzec 24–72 h [A]: po publicznym patchu spodziewać się (1) masowego skanowania, (2) PoC w godzinach, (3) ransomware/botów w 1–2 doby jeśli RCE jest wiarygodne. Przy AI BSI i Sansec zakładają godziny, nie dni [P/D][19:3][33:2].

11. Wnioski

Dla developerów aplikacji

Nie zakładajcie, że „bezpieczny kod aplikacji” chroni przed luką w runtime. Testujcie na wspieranych PHP; unikajcie polegania na rzadko używanych feature’ach pre-init (upload progress) bez potrzeby [A][3:12].

Dla ops / SRE

Inventory PHP włącznie z bundled (appliances, panele, kontenery). Patch window ≠ komunikat prasowy — weryfikujcie php -v / pakiet na każdym hoście. Plan B: izolacja internet-facing przy braku patcha [P][48:1][15:2].

Dla maintainerów OSS

Duże poprawki memory-safety potrzebują czasu i prenotyfikacji dystrybucji; jednocześnie wyciek embarga jest realnym scenariuszem — miejcie plan „release earlier” (PHP go miał i użył) [P][24:4].

Dla rządów / CERT

Profilaktyczne wyłączenia działają jako hamulec, ale kosztują zaufanie do usług publicznych. Listy zależności (NCSC-NL/php2shell) wzorem Log4Shell są wartościowe [P][16:4].

Dla mediów

Rozróżniajcie: oficjalne CVSS 9.2 vs plotki o 10.0; „early attacks” od CDN vs „brak misbruik” od CERT; nazwa społecznościowa vs komunikat vendora. Nie linkujcie niezweryfikowanych PoC jako „exploit” [A].

Aneks C: Lista kontrolna dla obrońców

Jak sprawdzić, że jesteście załatani — nie jak atakować.

  1. Zidentyfikujcie PHP: php -v na hostach; obrazy Docker; panele; appliances; Windows php.exe / php-cgi.exe [D][11:2].
  2. Docelowe wersje: ≥ 8.5.12 / 8.4.27 / 8.3.36 / 8.2.35; dla EOL — vendor LTS lub upgrade [P][3:13].
  3. Po update: restart wszystkich workerów (FPM reload/restart, Apache graceful/restart); sprawdźcie wersję w faktycznym SAPI, nie tylko CLI.
  4. Kontenery: po pojawieniu się tagów na Docker Hub — pull + redeploy; PR #1694 to dopiero początek łańcucha [P][36:1].
  5. Remi: nie czekajcie na dzisiejszy update Remi — dystrybucja lub build ze źródeł [P][37:1].
  6. Tymczasowo (nie zamiast patcha): środki z advisories; WAF vendorów jako stopgap [P][3:14][53:1].
  7. Hunting po fakcie: nietypowe child processy PHP (shell, curl, wget); webshelle; nowe pliki w docroot; worker churn; nietypowe multipart + 500 [D][11:3][4:19].
  8. EOL wystawione do Internetu: upgrade, VPN, lub offline [P][48:2][15:3].
